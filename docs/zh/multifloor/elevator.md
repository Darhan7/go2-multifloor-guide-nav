# 电梯流程：连续导航与离散状态切换怎样结合

## 当前任务

Nav2 擅长在一张二维地图中连续移动，但电梯会让机器人从一个 map frame 跳到另一个 map frame。当前方案采用人机协作：机器狗负责到达安全等待点，人负责开门、进入、乘坐和必要的姿态照看，系统负责状态提示与楼层切换。

## 为什么电梯不是普通路径上的一段

一条 Nav2 path 假设所有 pose 位于同一连续坐标系。进入电梯后：

- LiDAR 环境发生变化；
- 旧楼层地图不再适用；
- 电梯移动期间不存在从三楼 map 到一楼 map 的二维连续路线；
- 到达新楼层后需要加载新地图并建立新的初始位姿。

因此电梯更适合表示为**离散 transition**。

## 状态机是什么

状态机把任务拆成有限状态，并规定允许的转移：

```text
NAVIGATE_TO_ELEVATOR
→ WAIT_FOR_HUMAN
→ IN_ELEVATOR
→ SWITCH_FLOOR
→ LOCALIZE_ON_NEW_FLOOR
→ NAVIGATE_TO_DESTINATION
```

每个状态都有进入条件、完成条件、超时和失败处理。它不是必须使用某个特定库；核心是避免语音、导航和人工操作同时随意修改系统状态。

## 双方分别做什么

### 机器人/系统

- 导航到 `elevator_*_safe`；
- 停止 controller 并确认零速度；
- 语音提示等待人工操作；
- 到达目标楼层后切换地图和语义文件；
- 发布或请求新楼层初始位姿；
- 等待 `map → base` 可用后继续导航。

### 人

- 确认电梯安全、开门和空间；
- 协助机器人进入/离开；
- 处理电梯按钮和乘坐过程；
- 在系统无法可靠感知的情况下确认楼层到达。

## 地图切换不只是改文件名

完整切换至少涉及：

```text
停止当前导航 action
→ deactivate/stop 当前 map_server 和 AMCL
→ 加载目标楼层 YAML
→ 启动或重新配置 AMCL
→ 提供 initial pose
→ 等待 TF 收敛
→ 切换 semantic anchor set
→ 发送下一段 goal
```

若只替换 `/map` 而不重定位，机器人可能把旧楼层 pose 错误解释到新地图中。

## 为什么当前选择人机协作是合理的

全自主电梯需要门状态、按钮交互、轿厢定位、动态障碍和安全认证。当前项目的研究重点是导览导航与交互链，因此保留人类在高风险 transition 中，是一种明确的系统边界，而不是把未解决问题藏起来。

## 当前留下的可复用结构

- 每层独立地图和语义点；
- 电梯安全 anchor；
- building graph；
- 楼层对齐示意；
- 可连接语音提示和 Nav2 action 的任务编排设计。
